# Création assistée par IA

Dans **Paramètres → Création**, régler le nombre de décisions (40 par défaut), la durée totale (10 minutes par défaut), les instructions complémentaires, le rejeu avant validation et les questions pendant l’exploration. Les instructions complètent le protocole embarqué ; elles ne remplacent pas les contrôles techniques. La durée comprend les réponses aux questions et le rejeu.

L’action **Fichier → Modifier le projet courant…**, à côté de **Nouveau projet…**, permet de modifier son nom, ses plateformes, le package Android et le Bundle ID iOS. Ces applications peuvent aussi être renseignées lors de la création. L’application doit être installée. Cyberfox l’active avant l’exploration et l’exécution lorsqu’elle n’est pas au premier plan. Un identifiant vide conserve l’application courante. Renommer un projet conserve son dossier et ses scénarios.

La configuration permet de saisir un nom d’application ou de le lire depuis l’appareil associé. Android utilise ADB et les build-tools du SDK (`aapt`) pour lire le nom dans l’APK installé ; une icône PNG est récupérée lorsque la ressource peut être extraite avec `unzip`. Les icônes adaptatives non décodables restent sans aperçu. iOS lit le nom avec l’automatisation native lorsque disponible ; l’icône iOS n’est pas extraite. Le nom saisi manuellement et l’identifiant restent utilisables si la lecture échoue. Les informations détectées ne sont enregistrées qu’après validation du formulaire.

Chaque exploration enregistre une trace JSONL dans le sous-dossier `explorations` du projet : observations, interactions exécutées, erreurs, questions/réponses et proposition avec résultats de rejeu. Les champs sécurisés et les valeurs connues des variables projet et d’environnement `CYBERFOX_SECRET_*` sont masqués. Les écrans peuvent néanmoins contenir des données métier ; les traces restent locales. Une saisie dans un champ de mot de passe exige une référence `${VARIABLE_NAME}`.

L’IA organise l’arbre et ses assertions. Le moteur confronte chaque interaction proposée à une interaction réellement exécutée dans le même ordre sur le même OS, puis reconstruit sa variante à partir de cette trace. Une commande exécutée n’est pas, à elle seule, une preuve de réussite métier : le rejeu doit aussi passer des assertions.

Avant la popup de validation, le rejeu relance l’application configurée, sans effacer ses données, et compare l’écran obtenu à l’écran initial de l’exploration. Si cet état n’est pas retrouvé, il signale un échec sans exécuter les étapes proposées sur cet OS. Il respecte les préconditions, les enfants de secours et les étapes bloquantes. Les résultats Android et iOS sont séparés : réussi, échec, bloqué ou non exécuté. La validation manuelle reste possible en présence d’un échec ou d’une couverture incomplète.

Un rejeu réussi confirme l’exécution depuis l’état initial observé. Il ne prouve pas le fonctionnement depuis une installation neuve ou un compte vierge. Les ajouts restent en attente jusqu’à leur acceptation explicite ; les interactions d’exploration et de rejeu ont déjà eu lieu sur les appareils.

En mode Interactif, une demande de précision met en attente la même conversation IA. Le réglage « Autoriser les demandes de précision en mode interactif » ne concerne pas les confirmations de création des variables. En mode Auto-approve, aucune popup d’exploration ne s’ouvre ; les variables explicitement fournies sont enregistrées avant utilisation. La proposition finale reste à valider. Répondre permet de reprendre ; fermer la question ou arrêter annule l’exploration. Fournir des noms de variables pour les identifiants plutôt que leurs valeurs.
